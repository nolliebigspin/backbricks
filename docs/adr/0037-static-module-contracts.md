# ADR-0037: Static module contracts and borrowed capabilities

- **Status:** accepted
- **Date:** 2026-11-06
- **Task:** P1.6a; ARCHITECTURE §C.1–C.4; ADR-0019/0024/0035; approved Q5

## Context

The architecture's module sketch leaves heterogeneous configuration types, route/job registration and transaction ownership implicit. Passing the complete platform transaction to a module would expose key management and other modules' repositories. The registry must enforce declared capabilities and providers while preserving one physical transaction for collaborating modules. M1 has no operational domain modules; its complete definitions must remain test fixtures.

## Decision

[`defineModule`](../../packages/core/src/modules/define-module.ts) captures a typed [`ModuleDefinition`](../../packages/core/src/modules/contract.ts) and returns the normalized contract used by the static [`defineRegistry`](../../packages/core/src/modules/registry.ts). Each callback retains its inferred config/input/payload type through a closure; heterogeneous registration needs no `any`, unsafe cast or runtime plugin loader. Module packages augment the public `CapabilityMap` and `ModuleRepositories` interfaces with their contracts. Capability methods take the supplied `TenantHandle` first.

A registry frame projects one frozen handle from the actual `withTenant` transaction. Module callbacks receive that handle, their own repository binding, declared capability getters and restricted services. They never receive platform repositories, another module's repositories, the full service container, a driver or an unbound tenant selector. Bound services map only that exact handle to the caller transaction; capabilities reject foreign tenants with 404, separate frames/transactions with a safe internal error, and expired handles with the existing lifetime guard. A provider is instantiated lazily once per frame and receives its own module runtime. Static dependency validation orders providers before consumers, includes present optional dependencies and rejects cycles. Missing optional capabilities/providers are null; requiring an undeclared name fails both typing and runtime checks. This is an architectural boundary for trusted statically shipped code, not a sandbox for untrusted plugins.

The registry rejects duplicate types, singular/plural resources, scopes, events, metrics, providers, operation IDs, normalized method/path pairs and jobs. Module scope/event/metric/job names belong to their module namespace. Existing built-in module scopes may be claimed only by their owner; core scopes remain reserved. [`CORE_EVENTS`](../../packages/core/src/services/event-types.ts) now owns platform event names and their producers import it, allowing startup collision checks without a parallel event list.

Framework-neutral [route registration](../../packages/core/src/modules/routes.ts) captures Zod input and response schemas, body/auth/isolation policy, and explicit public read/write classification. The host remains responsible for auth, tenant binding, abuse controls and OpenAPI mounting in P1.6b/P1.9/P1.11. Native responses support declared JSON, empty, redirect and management CSV responses. JSON output is parsed through its declared schema and served as JSON, stripping undeclared fields or failing closed; public CSV is prohibited. Redirects are HTTP(S) without userinfo or secret-key values. CSV is an attachment; domain exports must still use the planned CSV escaping helper. Job registration captures a typed JSON-representable payload schema with explicit retries and retention of at most 30 days. Queue calls validate declared names/payloads and retain the caller transaction. Durable delivery/cron execution remains P1.10.

[Configuration normalization](../../packages/core/src/modules/configuration.ts) requires a representable JSON Schema, validates defaults/templates at startup and returns fresh JSON defaults. Current versions validate directly; older versions require the module migration hook, and future versions fail. Codegen and retention recomputation receive validated instances of the matching module/version. Canonical JSON comparison ignores object property order. A changed config without an explicit classifier is conservatively destructive; unchanged config is a no-op. Retention/privacy hooks validate their boundary inputs and result counts/JSON. No domain schema, production domain route, module-specific MCP tool or dynamic config migration is invented for M1.

Declarations are snapshots with frozen JSON metadata. Module event publication, usage increments/reads, entitlements and queue dispatch are restricted to declared names. Counters use the existing positive-bigint monthly service; declaring a gauge does not make counter increments valid. External providers remain the injected ports from ADR-0035.

## Evidence and consequences

`bun test packages/core/src/modules/registry.test.ts` covers valid/invalid registries, ordering, optional absence, dependency cycles, reserved names, required infrastructure, configuration/schema/migration/destructive defaults, route policy and job retention. The test-only [consumer/provider definitions](../../packages/db/test/module-fixtures.ts) import only the public core contract and Zod, and include compile-time negative checks for repository/capability/service access and capability argument types.

`bun test packages/db/src/module-registry.test.ts packages/db/src/capability-boundary.test.ts` uses migrated PostgreSQL: a consumer writes usage, calls a provider's scoped repository, emits an event and audits in the same transaction. A real failing audit constraint rolls back provider rows, usage and the event. Tests also cover foreign/separate/expired handles, registered jobs, public output snapshots and retention/privacy hooks. Regression tests first failed for inherited `constructor` cache entries and an HTML content type surviving JSON validation, then passed with own-property lookup and forced JSON content type. No database mock is used. Zod is added as a DB test dependency at the already-pinned workspace version solely to author these test definitions.

Production selection/mounting and truthful metadata remain P1.6b; generic instance/config endpoints remain P1.7. Passing the framework-only execution frame to a domain callback would violate this contract and I13.
