# ADR-0073: Complete subject exports and identity-free erasure settlement

Status: accepted during P3.7b execution on 2026-11-16; maintainer review deferred to M3 completion.

Subject privacy operations require every persisted project module to be enabled, using the same bounded availability guard as project erasure. Disabled historical data cannot silently disappear from an export or erasure result. Ordinary historical management reads retain their existing behavior.

ADR-0065 is implemented through optional module-owned attachment list/open hooks and one declared platform ZIP route. Hook registration requires declared storage, and all hook inputs/outputs are validated. The host commits the export-attempt audit before opening private bytes, opens each attachment in a fresh scoped read frame, and commits the completion audit before emitting the ZIP end marker. A generated-path STORE archive contains available ready bytes and a complete manifest explaining unavailable, expired, deleted, missing and quarantined files. Modules never reach across repositories. Forms-only archives contain metadata without storage.

[Export limits](../../packages/core/src/privacy/limits.ts) bound records per module, total UTF-8 metadata and archive bytes including directory overhead. Collection checks happen while accumulating; exceeding a bound fails explicitly. The previous Forms export could silently stop at 10,000 records. The streaming writer uses the runtime's incremental CRC32 and keeps one source reader plus a bounded central directory. Cancellation closes that reader; size, provider and audit failures prevent a valid end marker. Unexpected streaming errors are sanitized. Completion counts generated file entries; client disconnects can occur after the server's completion commit.

Subject erasure removes owner records and minimizes deleted-file metadata in the marker/audit/queue transaction. Names, subject email, user metadata, ownership and inspection fingerprints are removed immediately. A generated forward CHECK correction lets a marked-deleted ready record shed inspection evidence while keeping its original state and capacity accounting. Live ready records still require complete evidence. Only opaque identifiers, object/session identity and operational cleanup fields survive until physical removal is confirmed.

An optional module `pendingErasure` hook reports remaining physical work. A pending subject operation continues through `core.privacy.settle` using an opaque operation ID/count/round, without the subject email. Continuations wait at least 30 seconds. The uploads hook conservatively waits for every pending deletion in the project; this can delay one operation behind unrelated cleanup, avoiding a new workflow table or retained subject association. The initial email-bearing job keeps the existing bounded retention. Completion is audited only after physical work settles; provider failure remains pending and discoverable.

Real Postgres/Garage/ClamAV tests cover scoped JSON/ZIP contents, missing/EICAR exclusion, expiry after provider I/O, deterministic concurrent deletion, audit/enqueue rollback, immediate metadata minimization, storage outage/recovery and neighbour preservation. An independent ZIP reader verifies output; a 256 MiB generated stream proves bounded pull behavior. fflate 0.8.3 (MIT, registry/version and upstream documentation checked 2026-11-15) is a root development dependency used only as that independent reader. No runtime dependency or infrastructure is added.
